# Conditions, operators, UNKNOWN semantics, ordering and outcomes

## Input sources (fixed registry)

| Source | Field | Type / operators |
|---|---|---|
| `answer` | the **code of a question** of the rule set's checklist version | the question's Phase 5 answer type decides the operators (`operators_for`); comparison values are validated by that answer type (`clean_operand`); the input is the Phase 6 *answer state* (answered / empty / N/A / invalid / hidden) |
| `score` | `percentage`, `earned`, `available` | ordered decimals (`EQUALS`, `NOT_EQUALS`, `GREATER_THAN`, `GREATER_THAN_OR_EQUAL`, `LESS_THAN`, `LESS_THAN_OR_EQUAL`, `BETWEEN`, `NOT_BETWEEN`, `IS_EMPTY`, `IS_NOT_EMPTY`) |
| | `grade` | text, compared case-insensitively (`EQUALS`, `NOT_EQUALS`, `CONTAINS`, `STARTS_WITH`, ... ) |
| | `critical` | boolean (`EQUALS`/`NOT_EQUALS` `true`/`false`) |
| | `status` | one of `final`, `provisional`, `not_applicable`, `unavailable` |
| `execution` | `status` | `in_progress`, `submitted`, `cancelled` |

Operators for answers: `EQUALS`, `NOT_EQUALS`, `IS_EMPTY`, `IS_NOT_EMPTY`, `GREATER_THAN[_OR_EQUAL]`, `LESS_THAN[_OR_EQUAL]`, `BETWEEN`, `NOT_BETWEEN`, `CONTAINS`, `DOES_NOT_CONTAIN`, `STARTS_WITH`, `ENDS_WITH`, `SELECTED`, `NOT_SELECTED`, `CONTAINS_ANY`, `CONTAINS_ALL` - each only where the question's type allows it (see `docs/rule-operators.md`; list from `GET /api/v1/evaluation/metadata/`). A comparison between a string and a number, a malformed number, a float or an unknown option is **refused at validation**, never converted to zero.

### The score input

The score is read from the **stored current `ScoreResult`** of the execution - there is no calculation here. Its values are available only when that result is **final**. For a provisional result, a `not_applicable` result, an execution without a score, or a version whose scoring is off, the numeric / grade / critical fields are **unavailable** (an `INVALID` state: every operator gives UNKNOWN, `IS_EMPTY` included) and `score.status` is `provisional` / `not_applicable` / `unavailable`. A rule can test `score.status` explicitly ("when no score exists, require review"); a missing score is never compared as 0 %.

## Three-valued logic

Every comparison is TRUE, FALSE or UNKNOWN (the Phase 6 operators). A missing, empty, N/A, invalid, hidden or unavailable input is UNKNOWN for every operator except `IS_EMPTY` / `IS_NOT_EMPTY` on a question (an unanswered question is empty; N/A is neither empty nor answered).

| | AND | OR | NOT |
|---|---|---|---|
| rule | any FALSE -> FALSE; else any UNKNOWN -> UNKNOWN; else TRUE | any TRUE -> TRUE; else any UNKNOWN -> UNKNOWN; else FALSE | TRUE <-> FALSE; **UNKNOWN stays UNKNOWN** |

Only TRUE matches a rule. UNKNOWN never triggers an outcome or an action on its own and is never silently turned into FALSE: the rule is recorded as *undecided* with the missing input named, and `on_unknown` decides whether that also makes the evaluation INDETERMINATE.

## Ordering and conflicts

* Enabled rules run by `(priority, code)`. Equal priorities are a validation error, so the order is always explicit. Disabled rules never run.
* `stop` on a matched rule ends processing; later rules are recorded as *skipped* (with the rule that stopped them).
* **Outcome** = the highest precedence among the matched rules' outcomes: `FAIL` > `REVIEW_REQUIRED` > `INDETERMINATE` > `WARNING` > `PASS`. Every matched rule stays in the result; a critical match is never discarded by a milder one. A definite FAIL is never softened by an undecided rule.
* No enabled rule -> `NOT_APPLICABLE`; nothing matched -> `PASS`.
* Identical inputs, rules and engine version always give an identical result (the engine has no clock, randomness or database).

## Outcomes

`PASS`, `WARNING`, `REVIEW_REQUIRED`, `FAIL`, `INDETERMINATE`, `NOT_APPLICABLE` - one coherent set, separate from the execution, finding, corrective-action and workflow statuses.

## Explanations

Generated by the engine from the rule's configuration and the values actually observed, for example: *Rule “Low score review” matched because score status equals final (observed: final) and score percentage is less than 70 (observed: 62). The resulting outcome is REVIEW REQUIRED.* Undecided: *Rule “Rating low” could not be decided because the answer to “Cleanliness rating” (RATING) is less than 3 (observed: not answered).* The per-condition tree (with each leaf's TRUE / FALSE / UNKNOWN) is stored on the run and shown to people with `evaluation.explain`.
